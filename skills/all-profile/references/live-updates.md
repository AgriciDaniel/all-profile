# Apply approved profile changes

## Prepare a reviewable change

Identify the account from owner confirmation or an owned cross-link and confirm the active logged-in identity. Record the exact before values for affected fields, including link order and formatting. Store only the relevant profile information, not cookies, tokens, contact lists, or unrelated messages.

Present the proposed field diff, destination, visual choices, affected supporting surfaces, and material consequences. Link the user's approval to that version and scope. Reuse existing explicit authorization; do not ask again for unchanged approved actions. New copy, a different destination, or a broader account-setting change needs matching authorization.

Before mutation, compare the current editor with the before-state. If the owner or another process changed it meanwhile, reconcile the conflict instead of overwriting it. Note that names and handles may have cooldowns or other consequences, so copying an old value back may not be immediately possible.

## Operate through the available interface

Use the host's documented browser or connector tools. Inspect the live interface before selecting controls; labels and layouts can change. If the user requests a visible browser, keep that surface visible. Do not substitute hidden API evidence for requested visual verification.

For multiline descriptions, inspect the populated field before saving. Some text-setting methods flatten paragraphs in rich-text editors. Where supported, use plain-text paste or native multiline input and then read back the actual result. Never assume line breaks survived because the source string contains them.

Check the editor's own count and errors, especially with emoji and variation selectors. If the approved text does not fit, prepare the exact shorter alternative for approval unless equivalent adaptation was already authorized. Do not silently remove a claim's scope or change its meaning to save characters.

Save or publish only the approved changes. Treat surrounding defaults as meaningful: a network announcement, follower setting, public contact field, category, account type, or permission is outside a text edit unless explicitly included. Do not toggle it casually.

## Verify persistence and display

After saving:

1. Read the save response and any validation error.
2. Reload or reopen the field and compare actual saved text, links, and ordering.
3. Inspect the profile in a visitor view where available. State whether authenticated, logged out, desktop, or mobile. Do not claim views that were not inspected.
4. Expand collapsed bios and About sections. Check paragraph breaks, emoji, first visible lines, link labels, and destination. A working URL in a hidden admin field does not prove visitor access.
5. Save the actual after-state and evidence references, preserving the before-state and discrepancies.

A success toast alone supports “save reported success.” Persisted text supports “saved and reloaded.” Visitor inspection supports “verified on the inspected profile view.” None proves a conversion improvement.

## Bounded recovery and partial completion

If state appears stale, do one non-mutating reload/reopen and inspect before another write. Correct only an understood, authorized problem. If the same failure recurs, or identity, approval, or save state is uncertain, stop that field and report the evidence. Never repeatedly submit a possibly successful change.

If a field is mobile-only or absent, record the current value, desired value, exact manual next step, and blocker. Do not bypass it by converting accounts, buying a tier, using an undocumented endpoint, or exploring unrelated settings indefinitely. A failed link preview may justify proposing a relevant existing proof item; it does not authorize creating or posting new content.

Log in and complete CAPTCHA, MFA, or security verification through the user's normal flow. Do not request secret values in the report or attempt to bypass security challenges.

Partial completion is a normal outcome. Report each saved field and each pending one separately. A successful bio update does not close a mismatched website task. A visible old moderation notice does not establish current account health; report it separately only when relevant and keep investigation within the user's scope.

Rollback requires current-state checking and authorization appropriate to the change. Retained text is rollback evidence, not a guarantee that platform cooldowns or side effects can be reversed immediately.
